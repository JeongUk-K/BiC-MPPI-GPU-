# WMRobot Stitched Waypoint Sequential Example Review

This document describes the current `wmrobot/gpu_waypoint_순차추종`
experiment so another GPT model can review whether the implementation matches
the intended comparison design.

## Scope

The relevant files are:

```text
run_wmrobot_waypoint_stitched_sequential.sh
build_gpu.sh
src/wmrobot/gpu_waypoint_순차추종/stitched_barn_common.h
src/wmrobot/gpu_waypoint_순차추종/mppi.cpp
src/wmrobot/gpu_waypoint_순차추종/log_mppi.cpp
src/wmrobot/gpu_waypoint_순차추종/cluster_mppi.cpp
src/wmrobot/gpu_waypoint_순차추종/bi_mppi.cpp
visualize_wmrobot_waypoint_stitched.py
```

This is a separate experiment from `src/wmrobot/gpu_waypoint`. The purpose of
this folder is to compare MPPI-like solvers that sequentially follow waypoints
against BiC-MPPI, which builds bidirectional rollout connections over all
remaining waypoint segments and then runs one global guide step.

SVGD is intentionally excluded from this experiment.

## Scenario Generation

For each scenario:

1. A list of map ids is created from `0..dataset_maps-1`.
2. The list is shuffled using `seed + scenario_index`.
3. The first `maps_per_scenario` ids are selected.
4. Each selected map is loaded from:

```text
BARN_dataset/txt_files/output_<id>.txt
```

5. The maps are stitched by appending each map's columns:

```cpp
scenario.cols = cols * maps.size();
scenario.map[r][m * cols + c] = maps[m][r][c];
```

The resulting map is therefore longer along the planner's `y` direction because
the collision grid uses rows/cols as map axes and the waypoint path increases in
`y`.

## Waypoint Generation

Waypoints are generated by `makeWaypoints`.

The start is:

```text
x = start_x
y = 0
theta = pi / 2
```

The final goal is:

```text
x = start_x
y = map_length * maps_per_scenario
theta = pi / 2
```

Intermediate waypoints are linearly spaced between start and goal:

```cpp
alpha = i / (waypoint_count - 1)
y = total_length * alpha
```

Current C++ defaults in `stitched_barn_common.h` are:

```text
scenarios = 10
maps_per_scenario = 5
dataset_maps = 300
maxiter = 500
global_T = 500
waypoint_count = 6
waypoint_tolerance = 0.45
bic_Tf = 50
bic_Tb = 50
N = 3000
Nf = 3000
Nb = 3000
Nr = 1500
vis_every = 1
```

The effective default waypoint count is `6`, unless `--waypoint-count` is
provided.

## MPPI-Like Sequential Waypoint Following

MPPI, Log-MPPI, and Cluster-MPPI share `runMppiLikeScenario`.

The logic is:

1. Build the stitched map and collision checker.
2. Generate all waypoints.
3. Initialize the solver at `waypoints.front()`.
4. Initialize the first target as `waypoints[1]`.
5. For each closed-loop iteration:
   - Check collision at the current state.
   - Enable rollout logging if `iter % vis_every == 0`.
   - Set `solver.x_target = waypoints[target_index]`.
   - Call `solver.solve()`.
   - Call `solver.move()`.
   - Accumulate timing values.
   - Append the new state to `paths.csv`.
   - Check collision again.
   - If the robot is within `waypoint_tolerance` of the current waypoint,
     increment `target_index`.
   - Reset `U_0` after each waypoint transition.
   - Stop successfully if all waypoints are reached.

This means each MPPI-like solver performs one-direction GPU rollout toward the
current waypoint, not toward the final goal directly.

The metadata labels these solvers as:

```json
"target_mode": "sequential_waypoints",
"rollout_mode": "single_direction_parallel_gpu_rollouts"
```

## BiC-MPPI Behavior

BiC-MPPI uses `runBiScenario` with `WaypointBatchBiMPPI_GPU`.

The outer closed-loop still tracks progress with `target_index`, but the BiC
solve no longer targets only `waypoints[target_index]`. At each closed-loop
iteration, the code builds an anchor list:

```cpp
anchors = {
  solver.x_init,
  waypoints[target_index],
  waypoints[target_index + 1],
  ...,
  waypoints.back()
};
solver.solveWaypointGraph(anchors);
solver.move();
```

Inside `solveWaypointGraph`, each adjacent anchor pair is treated as one
waypoint segment:

```cpp
anchors[i] -> anchors[i + 1]
```

For every segment, BiC-MPPI runs:

1. backward rollout from the segment target,
2. forward rollout from the segment start,
3. clustering,
4. connection selection,
5. segment reference concatenation.

The best connected reference from each segment is then concatenated into one
global reference path from the current robot state to the final waypoint. After
that, `guideReference(Uref, Xref)` runs one global guide MPPI over the full
remaining waypoint route.

The current implementation still loops over waypoint segments on the CPU side
because `BiMPPI_GPU` natively supports one start-target pair per rollout call.
Within each segment, rollout samples are parallelized on the GPU. The final
guide step is one GPU guide rollout over the concatenated full-route reference.

The metadata labels BiC-MPPI as:

```json
"target_mode": "multi_waypoint_bidirectional_connections",
"rollout_mode": "all_remaining_waypoint_segments_forward_backward_gpu_rollouts_then_global_guide"
```

After `move()`, waypoint progress is still updated by checking whether the robot
is within `waypoint_tolerance` of the current target waypoint. This only affects
which waypoints remain in the next closed-loop iteration's anchor list.

## Success And Failure Criteria

The loop fails on collision:

```cpp
collision_checker.getCollisionGrid(solver.x_init)
```

The loop succeeds when `target_index >= waypoints.size()`, meaning all waypoint
targets have been reached.

After the loop, success is also set if the final state is within
`waypoint_tolerance` of the final goal:

```cpp
stats.success = stats.success ||
                (!stats.is_collision &&
                 stats.final_error <= cfg.waypoint_tolerance);
```

This means a run can be marked successful even if `reached_waypoints` does not
explicitly show that every intermediate waypoint was reached, as long as the
final pose is near the final goal. This may or may not match the intended
definition of waypoint sequential tracking.

## Timing Metrics

`summary.csv` stores per-scenario cumulative solver timings over closed-loop
iterations:

```text
elapsed
elapsed_rollout
elapsed_clustering
elapsed_connection
elapsed_guide
```

`timings.csv` stores the same solver timing fields for every completed
`solve() -> move()` step, plus cumulative values at that step:

```text
step
target_waypoint
reached_waypoints
elapsed
elapsed_rollout
elapsed_clustering
elapsed_connection
elapsed_guide
cumulative_elapsed
cumulative_rollout
cumulative_clustering
cumulative_connection
cumulative_guide
x
y
theta
```

For MPPI-like solvers, clustering/connection/guide may be zero or unused
depending on the solver. For BiC-MPPI, these fields are expected to capture the
extra bidirectional clustering/connection/guide stages.

## Review Questions For GPT

1. Does this experiment correctly separate the sequential waypoint-following
   comparison group from the original `gpu_waypoint` goal-direct experiment?
2. Is it conceptually fair that MPPI, Log-MPPI, and Cluster-MPPI optimize only
   the current waypoint, while BiC-MPPI optimizes a connected reference over all
   remaining waypoint segments?
3. Should BiC-MPPI segment rollout calls be made truly concurrent across
   segments, or is serial segment processing acceptable because each segment's
   samples already run in parallel on the GPU?
4. Should success require `target_index >= waypoints.size()` only, instead of
   also accepting final-goal proximity?
5. Should the effective default `waypoint_count` be `55` instead of `6`, given
   the experiment intent?
6. Should waypoint transition reset warm starts, or should the previous control
   sequence be shifted/reused across adjacent waypoint targets?
7. Is `waypoint_tolerance = 0.45` appropriate for BARN maps with
   `resolution = 0.1`, or is it too permissive?
8. Is stitching by columns and planning along the `y` direction consistent with
   the intended "vertical" or "horizontal" presentation?
9. Are `global_T = 500` for MPPI variants and `bic_Tf = 50`, `bic_Tb = 50` per
   waypoint segment for BiC-MPPI a fair budget comparison, or should rollout
   count and horizon be normalized differently?
10. Is comparing accumulated solver time across algorithms sufficient, or
    should the summary also report wall-clock scenario time, average step time,
    and number of waypoint transitions?

## Expected Review Outcome

The main point to verify is whether this implementation is the intended
comparison:

```text
MPPI variants:
  sequential waypoint targets, one-direction GPU rollouts

BiC-MPPI:
  all remaining waypoint segments are connected inside each closed-loop solve,
  then one global guide MPPI is run over the concatenated full-route reference
```

The remaining design question is whether segment rollout should be launched
truly concurrently across waypoint segments. The current code performs segment
rollout/connection serially at the host level, but every segment's rollout
samples and the global guide samples run on the GPU.
