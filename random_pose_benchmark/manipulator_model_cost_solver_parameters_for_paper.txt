Manipulator Random-Pose Benchmark: Model, Cost Function, and Solver Parameters
=============================================================================

Purpose of this document
------------------------
This document summarizes the manipulator dynamics model, forward kinematics,
collision model, cost function, and solver hyperparameters used in the
random_pose_benchmark experiments. It is written so the content can be used as
supporting material for the method/experiment section of a paper.

Code basis
----------

  src/manipulator/manipulator_workspace_collision_package/include/manipulator_dynamics_model.h

Important modeling caveat
-------------------------
The manipulator model used in this benchmark is not a full rigid-body
manipulator dynamics model of the form

  M(q) qddot + C(q, qdot) qdot + G(q) = tau.

Instead, the benchmark uses an RB5-like Denavit-Hartenberg forward-kinematics
chain together with a simplified decoupled joint-space second-order torque
model. This choice makes the benchmark suitable for comparing obstacle-aware
sampling MPC solvers, but it should not be described as hardware-accurate robot
dynamics.

Safe paper wording:

  "We evaluate the solvers in simulation using an RB5-like 6-DOF kinematic
   chain and a simplified decoupled joint-space second-order torque model."

Avoid wording:

  "We use the full rigid-body dynamics of an RB5 manipulator."


1. State, Control, and Continuous-Time Dynamics
===============================================

State and control
-----------------
The manipulator has six revolute joints. The state and input are

  x = [q; qdot] in R^12,
  u = tau in R^6,

where

  q     = [q1, ..., q6]^T        joint angles [rad],
  qdot  = [qdot1, ..., qdot6]^T  joint velocities [rad/s],
  tau   = [tau1, ..., tau6]^T    torque or torque-like command.

Continuous-time dynamics
------------------------
For each joint i, the dynamics are modeled independently as

  qdot_i = v_i,

  vdot_i = (sat(tau_i) - d_i v_i - g_i sin(q_i)) / I_i,

where

  v_i        = qdot_i,
  I_i        = joint inertia coefficient,
  d_i        = viscous damping coefficient,
  g_i        = sinusoidal gravity-amplitude coefficient,
  sat(tau_i) = clamp(tau_i, -tau_max_i, tau_max_i).

Equivalently,

  f(x,u) =
    [ qdot
      I^{-1} (sat(tau) - D qdot - g_amp .* sin(q)) ].

This is a stable torque-level benchmark model. It does not include coupling
terms between joints, Coriolis/centrifugal terms, or a configuration-dependent
mass matrix.

Numerical integration
---------------------
The executed closed-loop trajectory in the C++ benchmark is advanced with RK4:

  x_{k+1} = RK4(x_k, u_k, dt).

The GPU rollout model used inside MPPI sampling uses explicit Euler integration:

  x_{t+1} = x_t + dt f(x_t, u_t).

Thus, the benchmark uses RK4 for the executed simulation state and Euler
integration for sampled rollout evaluation on the GPU.

Time step
---------
All solvers use

  dt = 0.02 s.


2. Manipulator Dynamics Parameters
==================================

Joint limits
------------
The joint angle limits are

  q_min = [-2pi, -2pi, -165 deg, -2pi, -2pi, -2pi],
  q_max = [ 2pi,  2pi,  165 deg,  2pi,  2pi,  2pi].

In radians, the third joint limit is approximately

  165 deg = 2.87979 rad.

Velocity limits
---------------
The velocity limits are

  qdot_max = [2.0, 2.0, 2.0, 2.5, 2.5, 2.5] rad/s.

Torque limits
-------------
The torque or torque-like command limits are

  tau_max = [18.0, 18.0, 14.0, 8.0, 6.0, 4.0].

The control command is saturated componentwise before it is used in the
dynamics.

Second-order dynamics coefficients
----------------------------------
The decoupled joint dynamics use the following parameters:

  inertia I =
    [4.0, 3.5, 2.5, 0.9, 0.6, 0.35]

  damping d =
    [3.5, 3.2, 2.5, 0.8, 0.5, 0.35]

  gravity amplitude g_amp =
    [0.0, 7.0, 4.5, 0.6, 0.3, 0.15]

For example, joint 2 uses

  qddot_2 = (sat(tau_2) - 3.2 qdot_2 - 7.0 sin(q_2)) / 3.5.


3. Forward Kinematics
=====================

The benchmark uses an RB5-like 6-DOF Denavit-Hartenberg chain to compute joint
positions and the end-effector position.

The per-joint DH transform is

  A_i(q_i) =
    [ cos(q_i), -sin(q_i) cos(alpha_i),  sin(q_i) sin(alpha_i), a_i cos(q_i) ]
    [ sin(q_i),  cos(q_i) cos(alpha_i), -cos(q_i) sin(alpha_i), a_i sin(q_i) ]
    [        0,              sin(alpha_i),              cos(alpha_i), d_i    ]
    [        0,                         0,                         0, 1      ].

The cumulative transform is

  T_i(q) = A_1(q_1) A_2(q_2) ... A_i(q_i).

The end-effector position is the translation component of T_6:

  p_ee(q) = translation(T_6(q)).

DH parameters
-------------
The DH parameters are

  a     = [0.0, -0.427, -0.357, 0.0, 0.0, 0.0] m,
  d     = [0.15, 0.0, 0.0, 0.11, 0.09, 0.09] m,
  alpha = [pi/2, 0.0, 0.0, pi/2, -pi/2, 0.0] rad.

The link geometry used for collision checking is approximated by line segments
between the base origin and successive DH joint origins.


4. Workspace Obstacle and Collision Model
=========================================

Scenario obstacle placement
---------------------------
For each ordered start-goal pose pair, the benchmark places one axis-aligned
workspace box at the midpoint between the start and goal end-effector positions:

  c_obs = 0.5 (p_ee(q_init) + p_ee(q_goal)).

The box half sizes are

  half_size = [0.035, 0.035, 0.055] m.

The lower z bound is clamped by

  obstacle_min_z = 0.05 m.

Thus,

  xmin = c_x - 0.035,
  xmax = c_x + 0.035,
  ymin = c_y - 0.035,
  ymax = c_y + 0.035,
  zmin = max(0.05, c_z - 0.055),
  zmax = max(zmin + 0.02, c_z + 0.055).

Link collision approximation
----------------------------
The manipulator links are approximated as capsules or thick line segments with

  link_radius = 0.045 m.

For collision checking, sample points on each link segment are tested against
the obstacle AABB. The signed distance used by the model is

  sd_link = signedDistance(point, AABB) - link_radius.

A hard collision is declared if

  point_z < 0

or

  sd_link < hard_collision_margin,

with

  hard_collision_margin = 0.02 m.

Safe margin
-----------
The obstacle soft-cost safe margin is

  obs_safe_margin = 0.10 m.

CPU and GPU collision/checking details
--------------------------------------
The CPU model checks the two link endpoints and the link midpoint for each
segment. The GPU collision checker samples five points along each segment.
Both use the same DH geometry and link radius.


5. Cost Function
================

Stage cost
----------
The manipulator stage cost is

  l(x,u) =
      w_tau ||tau||^2
    + w_qdot ||qdot||^2
    + J_limit(q)
    + J_obs(x).

The weights are

  w_tau          = 1.0e-3,
  w_qdot         = 2.0e-2,
  w_joint_limit  = 20.0,
  w_workspace_obs = 2.0e3,
  w_ground       = 2.0e4.

Joint-limit penalty
-------------------
For joint i,

  center_i     = 0.5 (q_max_i + q_min_i),
  half_range_i = 0.5 (q_max_i - q_min_i),
  z_i          = (q_i - center_i) / (0.85 half_range_i),
  excess_i     = |z_i| - 1.

The joint-limit penalty is

  J_limit(q) = sum_i w_joint_limit max(excess_i, 0)^2.

Workspace obstacle penalty
--------------------------
Let

  sd = signedDistance(point, AABB) - link_radius.

The CPU model uses

  if point_z < 0:
      cost += w_ground point_z^2

  if sd < 0:
      cost += 1e5 + 1e5 sd^2

  else if sd < obs_safe_margin:
      e = (obs_safe_margin - sd) / obs_safe_margin
      cost += w_workspace_obs e^2.

The GPU rollout obstacle penalty uses a stronger hard-margin rule:

  if point_z < 0:
      cost += 1e5 + 1e5 point_z^2

  if sd < hard_collision_margin:
      cost += 1e6

  else if sd < obs_safe_margin:
      e = (obs_safe_margin - sd) / obs_safe_margin
      cost += 1e4 e^2.

Terminal/goal cost
------------------
The terminal or goal-attraction cost is

  Phi(x, x_goal) =
      w_terminal_q ||q - q_goal||^2
    + w_terminal_ee ||p_ee(q) - p_ee(q_goal)||^2
    + w_terminal_qdot ||qdot - qdot_goal||^2.

In this benchmark, qdot_goal = 0, so the final term becomes

  w_terminal_qdot ||qdot||^2.

The weights are

  w_terminal_q     = 1.5e3,
  w_terminal_ee    = 5.0e2,
  w_terminal_qdot  = 1.0e2.

Rollout objective used by the GPU solver
----------------------------------------
For sampled MPPI rollouts, the GPU cost accumulates both the stage cost and
the goal cost at each rollout step, and adds another goal cost at the final
state:

  J(U) = sum_{t=0}^{T-1} [ l(x_t, u_t) + Phi(x_t, x_goal) ]
       + Phi(x_T, x_goal).

For BiC-MPPI, the same stage and goal cost primitives are used for forward,
backward, and guide rollouts, with the relevant rollout target changing
depending on the branch direction.

Hard collision penalty
----------------------
If a sampled rollout enters hard collision, the sample is assigned a large
penalty:

  J_collision = 1e8.

Cluster-based solvers treat these samples as invalid for clustering whenever
the cost is at this collision-penalty scale.


6. MPPI Weighting and Control Update
====================================

Sample generation
-----------------
For forward MPPI-type solvers, the sampled control sequence is

  U_i = U_0 + Sigma epsilon_i,

where epsilon_i is standard Gaussian noise and Sigma is diagonal.

The noise standard deviations are

  sigma = [4.5, 4.5, 3.8, 2.2, 1.8, 1.2].

After sampling, controls are saturated by the torque limits.

Exponential weighting
---------------------
The MPPI weight of sample i is

  w_i = exp(-gamma_u (J_i - J_min)) / sum_j exp(-gamma_u (J_j - J_min)),

where

  J_min = min_j J_j.

The inverse-temperature parameter is

  gamma_u = 0.0015.

The output control sequence is the weighted average

  U_out = sum_i w_i U_i.

Closed-loop MPC execution
-------------------------
At each MPC iteration:

  1. The solver samples and evaluates candidate control sequences.
  2. It computes the selected or weighted output sequence U_out.
  3. The first torque command u_0 = U_out[:,0] is applied.
  4. The actual simulation state is advanced by one RK4 step.
  5. The nominal control sequence is shifted or rebuilt for the next iteration.


7. Benchmark Configuration
==========================

Pose-pair sweep
---------------
The benchmark uses a fixed set of 16 reference joint postures. It evaluates
all ordered start-goal pairs except self-pairs:

  scenario_count = 16 * 15 = 240.

The scenario order is

  for init_idx in [0, 15]:
    for goal_idx in [0, 15]:
      if init_idx != goal_idx:
        create scenario(init_idx, goal_idx).

Rollout seeds
-------------
Each scenario receives

  rollout_seed = 260800 + scenario_index.

Termination and success thresholds
----------------------------------
The maximum number of MPC iterations is

  max_iter = 200.

The strict binary success criterion is

  ||q - q_goal|| < 0.03,
  ||p_ee - p_ee,goal|| < 0.05,
  ||qdot|| < 0.2,
  collision_count = 0.

The result files also report decomposed metrics such as EE-only goal reaching,
collision-free rate, near-goal EE rate, and final continuous errors.

Warm start
----------
A PD torque warm start is used:

  tau = kp (q_ref - q) - kd qdot,

with

  kp = 18.0,
  kd = 7.0.

For forward solvers, the warm start first tracks an intermediate waypoint for
approximately half the horizon and then tracks the goal. For BiC-MPPI, separate
forward and backward warm starts are used.


8. Solver Hyperparameters
=========================

Common parameters
-----------------
All solvers use

  dt = 0.02 s,
  gamma_u = 0.0015,
  sigma = [4.5, 4.5, 3.8, 2.2, 1.8, 1.2].

MPPI
----
MPPI uses one forward rollout population:

  horizon T = 90,
  samples N = 1024,
  total samples per iteration = 1024.

The output control sequence is the MPPI weighted average over all sampled
control sequences.

Log-MPPI
--------
Log-MPPI uses the same horizon and number of samples as MPPI:

  horizon T = 90,
  samples N = 1024,
  total samples per iteration = 1024.

It uses the same Gaussian control sampling distribution as MPPI. The difference
is only in the weight normalization: Log-MPPI computes the exponential
trajectory weights in the log domain with log-sum-exp normalization:

  log_w_i = -gamma_u J_i,
  log_Z = log sum_j exp(log_w_j),
  w_i = exp(log_w_i - log_Z).

Collision-penalized rollouts with J_i >= 1e8 are excluded from the softmax.
If every rollout is collision-penalized, the solver uses the least-cost sampled
control sequence as a deterministic fallback.

Cluster-MPPI
------------
Cluster-MPPI uses the same forward rollout budget as MPPI:

  horizon T = 90,
  samples N = 1024,
  total samples per iteration = 1024.

It clusters valid sampled trajectories/control sequences using DBSCAN in a
low-dimensional control-sequence feature space. The feature is built by
dividing the horizon into three blocks and averaging each joint command within
each block.

Cluster parameters:

  cluster_deviation_mu = 1.0,
  cluster_epsilon = 3.8,
  cluster_minpts = 8.

For each cluster, a cluster-level MPPI weighted control sequence is computed.
The solver then chooses the best cluster candidate according to rollout cost
and collision feasibility.

BiC-MPPI
--------
BiC-MPPI uses bidirectional rollouts and a guide population:

  forward horizon Tf = 45,
  backward horizon Tb = 45,
  forward samples Nf = 1024,
  backward samples Nb = 1024,
  guide samples Nr = 1024,
  total samples per iteration = Nf + Nb + Nr = 3072.

BiC-MPPI parameters:

  bic_deviation_mu = 1.0,
  bic_cost_mu = 1.0,
  bic_epsilon = 3.8,
  bic_minpts = 8,
  bic_psi = 0.0.

At each MPC iteration, BiC-MPPI:

  1. Samples forward rollouts from the current state.
  2. Samples backward rollouts from the target state.
  3. Clusters forward and backward samples.
  4. Searches for compatible forward-backward branch connections.
  5. Concatenates the selected branch pair.
  6. Refines the concatenated reference through guide MPPI.
  7. Applies the first torque command of the selected trajectory.

Because BiC-MPPI uses 3072 total samples per iteration while the forward-only
baselines use 1024 samples per iteration, runtime and sample-budget comparisons
should be interpreted carefully. For equal-compute claims, a same-total-sample
baseline such as MPPI with N = 3072 should also be reported.

10. Suggested Paper Text
========================

The following paragraph can be adapted for the paper:

  "We evaluate the methods on a simulated 6-DOF manipulator benchmark. The
   manipulator uses an RB5-like Denavit-Hartenberg kinematic chain and a
   simplified decoupled joint-space second-order torque model. The state is
   x=[q, qdot] and the input is the joint torque command. Each joint follows
   qddot_i=(sat(tau_i)-d_i qdot_i-g_i sin(q_i))/I_i. Collision is evaluated
   using capsule-like link segments against an axis-aligned workspace obstacle.
   The MPPI rollout objective combines torque effort, joint velocity penalty,
   joint-limit penalty, workspace obstacle penalty, and a goal-attraction cost
   on joint error, end-effector position error, and residual joint velocity.
   We evaluate all 240 directed start-goal tasks generated from a fixed set of
   16 reference joint postures."

When reporting limitations, use:

  "The dynamics model is a simplified torque-level simulation model and is not
   intended to represent full rigid-body manipulator dynamics. The experiment
   is used to compare the relative behavior of sampling-based MPC variants
   under identical simulated conditions."
